# CLAUDE.md (transport/ice)

Notes for the ICE transport code. Checked against ice4j 3.2-18 (`ice4j` version in the root `pom.xml`). The keep-alive handling changed between ice4j releases, so check these notes again when the pin changes.

## ice4j behavior that affects the bridge

- The `Agent` changes to `TERMINATED` after `scheduleTermination()`, which runs when the state is `COMPLETED`, after `ice4j.ice.termination-delay` (default 3 seconds). The bridge does not override it. `Agent.terminate()` then stops the connectivity check client.
- After termination, ice4j does not ignore a check, but it can answer it with an error:
  - A check on a pair that ice4j did not know at termination (for example a new peer-reflexive address). `Agent.triggerCheck()` returns `false` and does not queue the pair. ice4j logs the warning "Received check for unknown candidate pair ... when client is stopped." `ConnectivityCheckServer` then sends a STUN Binding error response: 403 (FORBIDDEN, "Cannot add new remote candidates in current ICE state").
  - A check on a known pair that is not in the keep-alive pairs. This is the case for every pair except the selected pair under `selected_only`. `shouldRespondAfterTermination()` returns `false`, ice4j logs "Received connectivity check on non-keep-alive pair ... when ICE processing is terminated", and the answer is a 403.
  - A check on a pair that is in the keep-alive pairs (`Component.keepAlivePairs`) gets a success response.
  - A known pair that was not `SUCCEEDED` at termination can come back. When the client checks it, `recheckPairAfterTermination()` adds it to the keep-alive pairs and sends a consent check, if `wantsKeepAlive(pair)` is true (every pair under `all_succeeded`).
- Thus, when a client starts to send from a new local address after ICE at the bridge has ended (for example a cellular address after wifi fails), the bridge answers with a 403. It does not answer with success for an address that ice4j never built a pair for.
- The strategy `videobridge.ice.keep-alive-strategy` (`selected_only` is the default, `all_succeeded` is the other value) controls two things. `keepAlivePairs` is the set of pairs for which ice4j sends its periodic consent checks (`StunKeepAliveRunner`). It is also the set of pairs that get a success response to an incoming check after termination. Under `selected_only`, the set contains only the selected pair.
  - Under `all_succeeded`, a pair that reached `SUCCEEDED` stays in the set. A non-selected pair whose own consent checks time out leaves the set after `ice4j.keep-alive.failed-pair-timeout` (default 30 seconds), and ice4j does not add it again for 30 seconds. The set has at most `ice4j.keep-alive.max-pairs` (default 10) pairs. If it is full, ice4j evicts failed pairs first, and then the pairs with the lowest priority.
  - The bridge answers on a backup pair, but it keeps sending to the selected pair. `Component.send()` follows the address that the bridge last received from only when `ice4j.send-to-last-received-from-address` is `true` (default `false`), and ice4j never selects a pair again after `COMPLETED`.
- For a make-before-break failover design, the backup pair must pass its connectivity check before the `Agent` terminates (the termination delay, 3 seconds by default). A candidate that ice4j never knew (a peer-reflexive address from an unsignaled address, or a candidate that arrives after `COMPLETED`) can be used only after an ICE restart. `IceTransport` drops a late candidate with "Connection already established". A known pair that was not checked is re-checked under `all_succeeded` when the client first checks it.
- The bridge has an in-place ICE restart. `IceTransport.requestIceRestart()` creates a second `Agent` with a new ufrag and password. It keeps sending on the old selected pair, and it switches when the new `Agent` reaches `COMPLETED`. It frees the old `Agent` after `videobridge.ice.restart.transition-window` (default 3 seconds).
- An established `Agent` (`COMPLETED` or `TERMINATED`) never changes to `FAILED`. ice4j sets `FAILED` only during establishment: when it cannot build the check lists, or when all check lists end without success.
- Lost consent fails only single candidate pairs. `IceTransport.hasFailed()` and the `EventHandler.failed()` callback report only an ICE connection that never came up. A peer that went away after the connection is visible only through the activity timestamps: missing consent for a relay, and also `lastRtpPacketReceivedInstant` for an endpoint. To expire such a transport, use the activity timestamps, not ICE failure.
- ice4j refreshes consent only when it gets the response to its own consent check on the selected pair. `ConnectivityCheckClient.processSuccessResponse()` calls `setConsentFreshness()` only for the selected pair. Thus under `all_succeeded` the backup pairs that ice4j keeps alive do not refresh consent or activity. A check that the peer sends does not refresh consent. `IceTransport` also ignores consent events from a bundle that is not the current one, so the checks of a pending restart `Agent` do not refresh activity. The `consentUpdated` callback sets `packetIOActivity.lastIceActivityInstant`, which is part of `lastIncomingActivityInstant`. `Endpoint.shouldExpire()` and `Relay.shouldExpire()` use that value.
